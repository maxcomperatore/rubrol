Why Headless Chromium in Kubernetes Is an Architectural Mistake (And How We Cut PDF Memory by 95%)

By Rubrol Systems Team • October 7, 2026 • 11 min read

Every engineering team building PDF generation starts the exact same way. Someone installs Puppeteer or Playwright, writes a 20-line Node.js script using page.setContent() and page.pdf(), runs it on their local MacBook Pro, and remarks how effortless it was. The HTML looks just like the React dashboard. The task is marked as done.

Then the service gets deployed to a Kubernetes cluster.

Three weeks later, on a batch billing cycle or a high-concurrency surge, Slack begins lighting up with alerts. Pods are entering CrashLoopBackOff with exit code 137 (OOMKilled). SREs scramble to bump container limits from 1GB to 2GB, then 4GB. Soon after, the logs throw a new, terrifying error that more RAM cannot fix:

Error: spawn EAGAIN
    at Process.ChildProcess._handle.onexit (node:internal/child_process:284:19)
    at onErrorNT (node:internal/child_process: parent.js:477:16)
pthread_create failed: Resource temporarily unavailable

To survive, teams install CronJobs that reboot the pods every two hours. They add worker queues that throttle concurrency to 3 simultaneous renders. They write fragile retry loops. But the fundamental truth remains unaddressed:

The Fundamental Architectural Mismatch

A web browser is a continuous, stateful, multi-process desktop operating system designed to render interactive animations, execute untrusted JavaScript, and handle unbounded viewport scrolling. Stuffing it into an ephemeral, memory-capped Linux cgroup namespace to print static documents is an architectural anti-pattern.

The Anatomy of the "Pawan Bug": Why Chromium Dies in Containers

Let's dissect exactly why headless Chromium breaks down inside Linux container cgroups under real production traffic.

1. The cgroup v2 PID Exhaustion Trap (pids.max and EAGAIN)

When you call puppeteer.launch() or open a new browser context, you are not creating a thread. You are launching a cascade of Linux processes across separate namespaces:

  • The Browser Orchestrator Process (main event loop)
  • The Crashpad Handler (crash reporting and dump monitoring)
  • The GPU Process (even with --disable-gpu, software rasterization runs in an isolated worker)
  • The Network Service Process
  • The Zygote Process & Zygote Fork Sandbox (which forks individual Renderer processes for tabs)

In modern Kubernetes clusters running systemd with cgroups v2, every Pod belongs to a slice with an enforced pids.max limit (often set between 1,024 and 4,096 by the cluster's Kubelet configuration). Each Chromium process spawns dozens of internal pthreads for V8 garbage collection, Blink task scheduling, and IPC message loops.

When Node.js runs as PID 1 without an explicit init daemon (like tini or dumb-init), defunct child processes are not reaped when tabs close. Within hours of batch processing, zombie Chromium forks saturate the cgroup limit. When Node attempts to spawn another worker or Chromium tries to spin up a worker thread, the Linux kernel returns EAGAIN (Resource temporarily unavailable). No amount of container RAM will resolve a PID exhaustion panic.

2. The Multi-Layered Memory Leak (Blink, V8, and /dev/shm)

Why does Chromium trigger OOMKilled even when your JavaScript code cleanly calls page.close() and browser.close()?

Because Chromium's memory is fragmented across four decoupled heaps that do not coordinate with one another:

  1. The V8 JavaScript Heap: Managed by Node / V8 GC. Relatively small (~50MB).
  2. The Blink Layout & DOM Heap: C++ objects representing layout boxes, computed styles, and font tables. During a PDF export, Blink constructs an internal print layout tree. Detached DOM nodes frequently remain pinned in C++ memory even after V8 marks the JS wrappers as eligible for garbage collection.
  3. The Skia Graphics Surface: Renders vector paths into raster tiles. Font glyph cache textures linger across page evaluations.
  4. The Shared Memory Buffer (/dev/shm): Chromium uses POSIX shared memory to transfer pixel buffers between the Renderer process and the Browser process. Docker defaults /dev/shm to a microscopic 64MB. When developers bypass this via --disable-dev-shm-usage, Chromium falls back to writing raw IPC buffers directly to /tmp. On container filesystems (overlayfs), these ephemeral files hammer node disk IOPS and inflate the page cache, triggering kernel memory pressure and immediate cgroup slaughter.

3. CFS Bandwidth Throttling and Latency Spikes

Chromium is CPU-starved by design. Calculating CSS Cascading rules, flexbox reflows, and font metrics for a 30-page document requires sharp bursts of multi-core CPU. When run under Kubernetes Completely Fair Scheduler (CFS) quotas (cpu.cfs_quota_us), the kernel throttles Chromium the moment it exceeds its millisecond slice. A render that took 400ms locally spirals into a 5,000ms freeze, backing up the HTTP connection pool and compounding memory pressure.

The Root Flaw: The DOM Is the Wrong Abstraction for Pages

The web was built for an infinite scrollable canvas. An HTML <div> does not know what a physical sheet of paper is. It does not know margins, printable areas, page counters, or running headers.

CSS Paged Media (@media print, break-inside: avoid) is a fragile hack grafted onto a layout engine intended for screens. That is why multi-page invoice tables slice table rows directly across the middle of text glyphs. That is why repeating table headers fail intermittently across page boundaries.

The Solution: Native Document Compilation

Documents are not web pages. Documents are deterministic vector trees. By compiling structured data directly using an engine built for paginated typography—like Typst—we bypass the entire browser stack, saving 95% of memory and achieving sub-10ms latency.

How We Cut Memory by 95%: Zero-Process, Pure-Memory Layout

Rubrol is built from the ground up in Rust on top of the Typst typesetting ecosystem. It treats document generation not as a browser rendering exercise, but as a mathematical layout pipeline:

  • In-Memory Virtual Filesystem: When a request arrives, Rubrol ingests your JSON payload and Typst template into an in-memory typst::World. No files are written to /tmp. No disk I/O occurs.
  • Direct Vector Rasterization: Typst computes paragraph line breaking, hyphenation, and table paging using Knuth-Plass-style dynamic programming algorithms. Text glyphs are placed directly onto PDF content streams with native font subsetting.
  • Hermetic Memory Cleanup: The moment the PDF bytes are serialized, the Rust memory allocator (jemalloc) reclaims the workspace. There are no background event loops, no V8 garbage collection cycles, and zero retained memory buffers.

Frequently Asked Questions

Why does Puppeteer throw Error: spawn EAGAIN in Kubernetes?

The EAGAIN error indicates that the operating system kernel cannot allocate another process or thread. In Kubernetes, this occurs when Chromium's multi-process tree (Zygote, Crashpad, GPU, and Renderer forks) exhausts the pod cgroup's pids.max limit. If Node.js is PID 1 and fails to reap terminated child processes, zombie processes accumulate until the kernel blocks new allocations.

Why does Chromium get OOMKilled in Docker despite allocating 2GB+ of memory?

Chromium does not respect container memory limits cleanly. Blink's layout engine, Skia's rasterization caches, and IPC buffers (which spill into /tmp when --disable-dev-shm-usage is used) operate outside the V8 JavaScript heap. Under batch traffic, these uncollected C++ memory structures cause the container's Resident Set Size (RSS) to spike past the cgroup memory limit, prompting the Linux kernel OOM killer to terminate the container with exit code 137.

Can I generate PDFs without HTML or CSS?

Yes. Document layout languages like Typst use concise, functional markup designed specifically for print pagination. You provide structured data (JSON), which is mapped to Typst templates that feature built-in page geometry, automatic table headers across breaks, and precise typographical kerning—without running a web browser.

Yes. Rubrol is fully open-source under the Apache 2.0 license, written in memory-safe Rust, and deployed in high-volume fintech and invoicing pipelines compiling thousands of compliant PDF/A-3b and Factur-X documents per second.
